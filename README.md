# DataFarm-X

[![CI](https://github.com/zkaoudi/Datafarm-X/actions/workflows/ci.yml/badge.svg)](https://github.com/zkaoudi/Datafarm-X/actions/workflows/ci.yml)

DataFarm-X generates and labels large workloads of realistic jobs for ML-based data management (learned cost
models, learned query optimizers, ...). It extends [DataFarm](#citation), which generated Flink jobs, to several
platforms ("X"): **Flink, Apache Wayang, Spark, SQL (PostgreSQL, DuckDB) and SQL Server**, over the **TPC-H** and
**Join Order Benchmark (JOB)** datasets and **any dataset you add** from its schema, a few seed queries and the data.

DataFarm follows a data-driven, white-box approach. It learns the patterns of a small input workload (operator
sequences, number of joins, plan depth) as *abstract plans*, then instantiates each abstract plan into concrete jobs
by choosing tables, joins, filters and group-by fields from the dataset's metadata. A label forecaster then runs a
few of the jobs and predicts the run times of the others with active learning.

For a given plan and seed, every platform gets the same tables, joins, filters and group-by fields. The workloads
are therefore comparable across platforms, for example the same job as a Wayang plan, a Spark program and a SQL query.

## Quick start

Generating jobs needs Python ≥ 3.8 with three packages, and sbt (the job generator is a Scala project; sbt downloads
Scala and the other dependencies on the first run).

```bash
git clone https://github.com/zkaoudi/Datafarm-X.git
cd Datafarm-X
pip install -r requirements.txt          # numpy, pandas, networkx
python RunGenerator.py --platform SQL --dataset JOB --plans 10 --versions 2
```

This writes 10 × 2 jobs to `training-data/SQL_JOB/generated_jobs/`: `Job0v0.sql`, `Job0v1.sql`, ... and
`generated_jobs_info.json`, which describes every operator of every job (tables, filters with their selectivities,
joins, group-by fields). For example, `Job11v0.sql`:

```sql
-- Generated by DataFarm from the job schema: Job11v0
WITH
source0 AS (
  SELECT * FROM company_name
),
filter1 AS (
  SELECT * FROM source0 WHERE country_code = '[us]'
),
source3 AS (
  SELECT * FROM movie_companies
),
join2 AS (
  SELECT r.* FROM filter1 l JOIN source3 r ON l.id = r.company_id
),
reduce4 AS (
  SELECT id, movie_id, company_id, company_type_id, note FROM (SELECT *, ROW_NUMBER() OVER (ORDER BY id NULLS FIRST, movie_id NULLS FIRST, company_id NULLS FIRST, company_type_id NULLS FIRST, note NULLS FIRST) AS datafarm_rn FROM join2) ranked WHERE datafarm_rn = 1
)
SELECT * FROM reduce4;
```

Run the jobs on your own data and system (see the [platform](#platforms) and [dataset](#datasets) sections). To also
label them with run times, see [Labeling jobs](#labeling-jobs) (optional).

### Options

| Option | Meaning | Default |
|---|---|---|
| `--platform` | `Flink`, `Wayang`, `Spark`, `SQL`, `SQLServer` or `SQLServerFlat` ([which datasets each supports](#platforms-and-datasets)) | `SQL` |
| `--dataset` | `TPCH`, `IMDB`, or a dataset folder in [`datasets/`](datasets/) such as `JOB` or `example` (names are case-insensitive), or the path of one | `TPCH` |
| `--workload` | input workload the shape of the jobs is learned from: a folder in [`input-workloads/`](input-workloads/) (e.g. `tpch`, `job`) or a folder of Flink plans (`*.json`) or SQL queries (`*.sql`); see [input workloads](datasets/README.md#input-workloads) | the workload named like the dataset, or its seed queries |
| `--plans` | number of abstract plans learned from the input workload | 10 |
| `--versions` | jobs per abstract plan, each with different tables, filters and group-by fields; total = plans × versions | 2 |
| `--seed` | the same seed gives the same jobs. The seed of each job is derived from it and the plan index, so different plans still differ; `-1` derives it from the plan index only (also deterministic) | 42 |
| `--experiment` | name of the output folder | `<platform>_<dataset>` |
| `--output` | folder in which the experiment folder is created | `training-data/` |
| `--table-prefix` | `SQLServerFlat` only: prefix of the table names, e.g. `tpch.dbo.` | none |

For a given seed, all platforms get the same jobs: run the same command with another `--platform` to get the same
workload as, say, Wayang plans or Spark programs. The defaults of these options, and the settings of the label
forecaster, are in `CONFIG.py`.

### Requirements

- **Generating jobs:** Python ≥ 3.8 (tested with 3.8, 3.12 and 3.13) with `requirements.txt`, a JDK (8 or later) and
  sbt ≥ 1.3. Optional: `matplotlib` and `pygraphviz` draw a PDF of each abstract plan (`pip install -e ".[plots]"`).
- **Running the generated jobs:** the platform itself; see each platform's section.
- **Labeling jobs:** Python 3.6–3.8 with `requirements-labeling.txt`, and a Flink 1.10 cluster; see
  [Labeling jobs](#labeling-jobs).

DataFarm-X has been tested on Linux and macOS. `docker-compose.yml` sets up a container with sbt, Scala and Python
in which the repository is mounted at `/usr/src/app`.

## Platforms and datasets

Choose the platform with `--platform` and the dataset with `--dataset` (`TARGET_PLATFORM` and `DATA_MANAGER` in `CONFIG.py`).

| `--platform` | Output | TPC-H | JOB and other [dataset folders](#your-own-dataset) |
|---|---|:---:|:---:|
| `Flink` | an sbt project per job (Flink DataSet API) | ✓ | ✓ |
| `Wayang` | `JobXvY.scala` (Wayang Scala API) | ✓ | ✓ |
| `Spark` | `JobXvY.scala` (RDD API) and a `build.sbt` | ✓ | ✓ |
| `SQL` | `JobXvY.sql` (standard SQL) and `schema.sql` | ✓ | ✓ |
| `SQLServer` | `JobXvY.sql` (T-SQL) and `schema.sql` | ✓ | ✓ |
| `SQLServerFlat` | `JobXvY.txt` (flat T-SQL, no CTEs), with `JobXvY.json` and `JobXvY.pickle` describing each query | ✓ | |

The `IMDB` dataset (the Kaggle IMDb dump) comes from the original DataFarm and supports Flink only.

## Repository layout

All code is in the `datafarm/` package; data, output and experiments sit beside it. Inside `datafarm/`, the folders
follow the three components of DataFarm: abstract plan generation, instantiation and labeling, plus dataset metadata and
job execution. Abstract generation writes abstract plans as JSON files, which instantiation reads, so each side can
change independently.

| Folder | What it contains |
|---|---|
| `datafarm/abstract_generation/` | **Abstract plan generation** (Python). `generate_abstract_plans.py` learns operator transitions from an input workload (`AbstractPlan.py`, `Node.py`, `ExecutionPlanTools.py`, `FeatureExtraction.py`) and writes abstract plans. `tpch_input_workload/` holds the Flink TPC-H query jobs whose execution plans form the TPC-H input workload (its own sbt project). |
| `datafarm/instantiation/` | **Instantiation** (Scala, sbt project). `instantiation.JobGenerator` turns abstract plans into jobs: `platform/{flink,wayang,spark,sql}` translates operators for each platform. `dataset/generic` generates the jobs of every dataset folder from its `catalog.json`; `dataset/{tpch,imdb}` hold the schemas, joins, filters and statistics of TPC-H and IMDB in Scala. |
| `datafarm/labeling/` | **Label forecasting** (Python): features, job sampling, the quantile-forest model and the Flink task-manager client used by `RunLabelForecaster.py`. |
| `datafarm/datasets/` | **Dataset folders** (Python): `add_dataset.py` derives a dataset's `catalog.json` from its schema, seed queries and data (`schema.py`, `queries.py`, `analyze.py`); `workload.py` translates SQL queries into input plans; `csvformat.py` reads the data files as the generated jobs do. |
| `datafarm/datasets_metadata/` | Metadata of TPC-H and IMDB (`tpch/`, `imdb/`): `MetaDataAnalyzer.py` computes the statistics the job generator uses (filter selectivities, distinct group-by values) from the data; `TableMetaData.py` holds the table schemas and cardinalities. |
| `datafarm/execution/` | **Execution**: tools that run generated jobs and collect their run times or plans, used for labeling. `flink/run_flink_jobs.py` compiles and runs Flink jobs locally and `flink/BuildAndSubmit.py` submits them to a cluster; `spark/run_spark_jobs.py` builds and runs Spark jobs; `wayang/run_wayang_jobs.py` compiles and runs Wayang jobs; `sql/` loads data into DuckDB, PostgreSQL or SQL Server and runs SQL jobs there. |
| `datasets/` | **Datasets defined by a folder** ([README](datasets/README.md)): `job/` and `example/`, each with `schema.sql`, `dataset.json`, seed queries and the derived `catalog.json`. |
| `input-workloads/` | Input workloads abstract plans are learned from, kept apart from the datasets: `tpch/` (Flink execution plans of TPC-H queries) and `job/` (the 113 JOB queries translated into plans). |
| `training-data/` | **Output**, one folder per experiment (`--experiment`, default `<platform>_<dataset>`): abstract plans, generated jobs, their execution plans and labels; see its [README](training-data/README.md). Not tracked by git. |
| `experiments/` | Scripts and configurations of the DataFarm paper's experiments; not used by the pipeline. |

The entry points `RunGenerator.py` and `RunLabelForecaster.py` and the configuration `CONFIG.py` are at the top level.
To use the Python code from other projects (e.g. the abstract plan generator), install it from a clone with
`pip install -e .` and import it as `datafarm.abstract_generation`, `datafarm.datasets_metadata`, etc.

## Platforms

The same plan gives the same result on every platform. Joins keep the right-hand row. A group-by (or keyed Reduce)
keeps one whole row per key and a global Reduce one row, so later operators see the table's columns: the smallest
row, comparing all columns in order with nulls first. On Flink, Spark and Wayang this is the reduce function
`minRecord` (generated into each job), which is associative and commutative as these engines require, so the kept row
does not depend on the engine, the partitioning or the order in which rows arrive. SQL keeps the same row with
`ROW_NUMBER()`.

### Flink

The original DataFarm target. Each job becomes an sbt project `JobXvY/` (`build.sbt`, `project/plugins.sbt` with
sbt-assembly, `src/main/scala/JobXvY.scala`) using the Flink DataSet API.

- **Versions:** Flink 1.10 with Scala 2.11. Flink 1.10 runs on Java 8 or 11, not on Java 17 or later.
- **Running a job:**
  `JobXvY <data_path> <exec_plan_out_path> <exec|noexec> <local|nolocal> <heap_size> <parallelism>`.
  With `exec`, the job runs and writes `<exec_plan_out_path>/JobXvY$.json` with Flink's execution plan and the net
  run time. `datafarm/execution/flink/BuildAndSubmit.py` builds the projects with `sbt assembly` and submits them with `flink run`.
- **Running all jobs locally:** `datafarm/execution/flink/run_flink_jobs.py` compiles all job projects of a folder
  at once, runs each job in its own JVM with Flink's local environment and writes a CSV with, per job, the status,
  the number of output rows (jobs of [dataset folders](#your-own-dataset), whose sink counts its rows), Flink's net
  run time, the wall-clock time and the error:

  ```bash
  python datafarm/execution/flink/run_flink_jobs.py training-data/<experiment>/generated_jobs \
    --data /path/to/data/ --output results.csv [--parallelism 2] [--timeout 600]
  ```

- **Datasets:** all (and IMDB from the original DataFarm). TPC-H jobs read the `.tbl` files with Flink's CSV reader;
  the jobs of dataset folders parse their files themselves, like the Wayang and Spark jobs.

### Wayang

Each job is a standalone Scala object in package `datafarm.generated.wayang` that uses only the public
[Apache Wayang](https://github.com/apache/incubator-wayang) Scala API. `buildPlan(planBuilder, datapath)` builds the
plan and returns its final `DataQuanta` without executing it; `main` runs it.

- **Versions:** the generator writes a `build.sbt` next to the jobs for Apache Wayang 1.1.1 (the latest release on
  Maven Central; Scala 2.12, Java 17), with `wayang-api-scala-java`, `wayang-java` and `wayang-spark`. To build
  against Wayang's main branch instead, run `mvn install -DskipTests` in a Wayang checkout, set `wayangVersion` in
  the `build.sbt` to its version (e.g. `1.1.2-SNAPSHOT`) and uncomment the `Resolver.mavenLocal` line.
- **Running all jobs:** `datafarm/execution/wayang/run_wayang_jobs.py` compiles the jobs with sbt, then runs each
  one in its own JVM and writes a CSV with, per job, the status (`ok`, `error` or `timeout`), the number of output
  rows, the run time the job measures (building, optimizing and executing the Wayang plan, without JVM start-up),
  the wall-clock time, and the error:

  ```bash
  python datafarm/execution/wayang/run_wayang_jobs.py training-data/<experiment>/generated_jobs \
    --data /path/to/data/ --output results.csv [--platforms java|spark|java,spark] [--timeout 600]
  ```

  It needs Java 17 or later and sbt. `--platforms` lists the platforms Wayang may choose from (default `java`);
  with several, Wayang's optimizer picks one per operator. `--jvm-option` passes JVM options (e.g.
  `--jvm-option=-Xmx8g`), `--jobs` runs only some jobs, and `--no-build` reuses the classpath of the last build.
- **Running one job:**

  ```bash
  cd training-data/<experiment>/generated_jobs
  sbt "runMain datafarm.generated.wayang.Job0v0 java /path/to/data/"
  ```

  The first argument is the platforms Wayang may use: `java`, `spark` or `java,spark`. The data path can be a local
  folder or a URL. A job collects the output of its plan and prints the row count and run time.
- **Parsing:** each job parses its own input (object `JobXvYParsers` in the same file): TPC-H `.tbl` files, or the
  files of a dataset folder in its format, so no dataset classes are needed in Wayang. TPC-H dates become `Int`s (year * 365 + month * 30 + day),
  which the generated date filters compare against.

### Spark

Each job is a standalone Scala object in package `datafarm.generated.spark`, using the RDD API with one
transformation per plan operator. Spark therefore runs exactly the generated plan: Catalyst does not re-optimize
filters or join order.

- **Versions:** the generator writes a `build.sbt` for Spark 3.5.3 and Scala 2.12 (`provided`) next to the jobs.
- **Running all jobs:** `datafarm/execution/spark/run_spark_jobs.py` builds the jobs with `sbt package`, submits
  each one with `spark-submit` and writes a CSV with, per job, the status (`ok`, `error` or `timeout`), the number of
  output rows, the net run time the job measures (its `count()`, without start-up), the wall-clock time of the
  submit, and the error:

  ```bash
  python datafarm/execution/spark/run_spark_jobs.py training-data/<experiment>/generated_jobs \
    --data /path/to/data/ --output results.csv [--master local[*]] [--plans plansDir] [--timeout 600]
  ```

  It uses `$SPARK_HOME/bin/spark-submit`, or `spark-submit` from the `PATH`; `pip install pyspark==3.5.3` provides
  one. Use a Spark 3.5 build for Scala 2.12. `--conf KEY=VALUE` and `--driver-memory` are passed to `spark-submit`,
  `--jobs` runs only some jobs, and `--no-build` (or `--jar`) skips the build.
- **Running one job:**

  ```bash
  cd training-data/<experiment>/generated_jobs
  sbt package
  spark-submit --class datafarm.generated.spark.Job0v0 target/scala-2.12/datafarm-spark-jobs_2.12-0.1.jar \
    /path/to/data/ [planOutputDir]
  ```

  The data path must end with `/`. A job runs its plan with `count()` and prints the row count and run time. With
  `planOutputDir`, it also writes `JobXvY.json` with the run time, row count and RDD lineage (`toDebugString`).
- **Parsing:** each job parses its own input (object `JobXvYParsers` in the same file): TPC-H `.tbl` files, or the
  files of a dataset folder. The parsers are the same as in the Wayang jobs, so date filters behave the same on both.
- **Semantics:** as on all platforms (see [Platforms](#platforms)), joins keep the right-hand tuple and reduces keep
  the smallest row. Whether a reduce is keyed comes from the input workload: Flink's driver strategies tell
  (`Reduce All` is global, `Sorted Reduce` keyed), and in SQL queries an aggregate without `GROUP BY` is global. Keyed
  reduces become group-bys and global ones reduces. TPC-H's hand-written table managers still make a Reduce pair a
  keyed reduce, until TPC-H moves onto the dataset folders.

### SQL

With `--platform SQL`, each job is one standard-SQL statement in `JobXvY.sql`, tested with PostgreSQL 16
and DuckDB.

- **Structure:** every plan operator becomes a common table expression named like the variables of the dataflow
  jobs (`source0`, `filter1`, `join2`, ...), and the job returns the output of the last one.
- **Schema:** the generator writes `schema.sql` next to the jobs: the `CREATE TABLE` statements, with load commands
  for PostgreSQL and DuckDB in its header. TPC-H uses dbgen's column names (`l_orderkey`, ...). For dataset folders,
  the tables are those of the dataset's `schema.sql`, with integer columns as integers and all other columns as text
  (`VARCHAR(n)` or `TEXT`), as the dataflow jobs read them.
- **Operators:** joins keep the right-hand rows, as in the dataflow jobs. A group-by (or keyed Reduce) returns the
  smallest row per key and a global Reduce the smallest row (`ROW_NUMBER() OVER (... ORDER BY <all columns>) = 1`),
  the same rows the dataflow jobs keep. Maps and partitions pass their input through, since their UDF cost has no
  SQL counterpart.
- **Optimization:** unlike Wayang, Flink and Spark, which run the generated plan as written, the database optimizes
  the query: it may reorder joins and push down filters. That suits training data for learned query optimizers.
- **Result sizes:** the same as on the dataflow platforms. Text columns are compared with the database's collation,
  which can differ from Java's order only between rows that agree on all earlier columns; TPC-H and JOB rows start
  with their key columns, so this does not happen. Range filters on text (`<`, `BETWEEN`) can also select
  differently under a collation other than code-point order (`C`), except on digits-only text such as ISO dates.

#### Loading data and running SQL jobs

`datafarm/execution/sql/` has one loader and one runner for all SQL targets; `--engine` picks the database:

| `--engine` | Jobs (`--platform`) | `--connection` | Python package |
|---|---|---|---|
| `duckdb` | `SQL` | database file (default `datafarm.duckdb`) | `duckdb` |
| `postgres` | `SQL` | libpq connection string or `postgresql://` URL | `psycopg[binary]` |
| `sqlserver` | `SQLServer`, `SQLServerFlat` | ODBC connection string (needs an ODBC driver for SQL Server) | `pyodbc` |

The connection can also be set in the environment variable `DATAFARM_DUCKDB`, `DATAFARM_POSTGRES` or
`DATAFARM_SQLSERVER`.

```bash
# create the tables of schema.sql and load the data
python datafarm/execution/sql/load_sql_data.py --engine postgres --dataset TPCH --data /path/to/tpch \
    --schema training-data/<experiment>/generated_jobs/schema.sql --connection "host=… dbname=… user=…"
# run all jobs of a folder (JobXvY.sql or JobXvY.txt)
python datafarm/execution/sql/run_sql_jobs.py training-data/<experiment>/generated_jobs --engine postgres \
    --connection "…" --output results.csv [--timeout 600] [--plans plansDir]
```

- **Loading:** `--dataset` is `TPCH` or a dataset folder (e.g. `job`). The loader parses the files as the generated
  Flink, Wayang and Spark jobs do (for a dataset folder, with the file format of its `catalog.json`), so every
  platform sees the same data; the databases' own CSV readers handle some files differently (for example JOB's
  backslash escapes). It loads with `COPY` in PostgreSQL, in batches in DuckDB and SQL Server. `--truncate` deletes
  existing rows first and `--tables` loads only some tables.
- **Running:** the runner writes a CSV with, per job, the status (`ok`, `error` or `timeout`), the number of rows
  of the result, the run time (executing the query and fetching its result), and the error. `--jobs` runs only some
  jobs. With `--plans DIR`, it saves each job's estimated plan instead of running it: `EXPLAIN (FORMAT JSON)` in
  DuckDB and PostgreSQL (`JobXvY.json`), `SHOWPLAN_XML` in SQL Server (`JobXvY.xml`).

### SQL Server

Two targets generate jobs for Microsoft SQL Server.

**`--platform SQLServer`** (TPC-H and dataset folders) writes the [SQL](#sql) jobs in T-SQL:

- dates as `CAST('…' AS DATE)`;
- sorts inside a common table expression with `OFFSET 0 ROWS` (SQL Server rejects a plain `ORDER BY` there);
- `[` escaped in `LIKE` patterns.

Its `schema.sql` uses, for TPC-H, the column types of dbgen's `dss.ddl` and the primary keys of `dss.ri`. For dataset
folders, text columns are `NVARCHAR` with the lengths of the dataset's `schema.sql` and a binary collation, so text comparisons are
case-sensitive as on the other platforms (SQL Server's default collations are not).

**`--platform SQLServerFlat`** (TPC-H only) writes each job as one flat query, without CTEs, together with a
structured description of it:

- `JobXvY.txt` holds the query (`SELECT … FROM t1, t2 WHERE … GROUP BY … ORDER BY …`).
- `JobXvY.pickle`, written by `RunGenerator.py` from `JobXvY.json`, holds the same query as a dict with the keys
  `FROM`, `SELECT`, `WHERE`, `WHERE_JOIN`, `GROUP BY` and `ORDER BY`.
- Filters, joins and group-bys come from the plan. Maps become columns or `COUNT`/`AVG`/`SUM`, and sorts become
  `ORDER BY` items.
- Every query is valid SQL Server: no table occurs twice in `FROM` (the format has no aliases),
  and grouped queries select and sort only group columns and aggregates.
- Pass `--table-prefix` (e.g. `--table-prefix tpch.dbo.`) to qualify the table names.
- Dataset folders are not supported: the format stores one column name per join, so a join like
  `cast_info.movie_id = title.id` cannot be expressed.

**Loading data and running jobs:** see [Loading data and running SQL jobs](#loading-data-and-running-sql-jobs), with
`--engine sqlserver`. For TPC-H, `BULK INSERT` (see the header of `schema.sql`) loads faster than the loader; JOB's
files need the loader, since `BULK INSERT` cannot read their backslash escapes.

## Datasets

### TPC-H

`--dataset TPCH`. All platforms.

- **Data:** the `.tbl` files generated by TPC-H's dbgen (`|`-separated). A sample of about 1 GB is available
  [on Kaggle](https://www.kaggle.com/fven7u/tpch-1gb).
- **Input workload:** `input-workloads/tpch/`, Flink execution plans of TPC-H queries 1, 3, 11, 13, 17 and
  21 (hand-written and SQL versions). Generated plans have at most depth 6 and 3 joins (`INPUT_WORKLOAD` in
  `CONFIG.py`). You can add any execution plan extracted from Flink jobs.
- **Metadata:** each table's join fields, filter fields with values and selectivities, and group-by fields with
  their number of distinct values are defined in the table managers
  (`datafarm/instantiation/src/main/scala/instantiation/dataset/tpch/`). To recompute them for your own data, run
  `python datafarm/datasets_metadata/tpch/MetaDataAnalyzer.py /path/to/tbl_dir`, which prints them as Scala maps
  to paste there. `datafarm/datasets_metadata/tpch/TableMetaData.py` holds the table cardinalities for scale factors
  1, 5, 10 and 50 GB, which the label forecaster uses.

### Join Order Benchmark (JOB)

`--dataset JOB`. The IMDB database of the Join Order Benchmark
([Leis et al., PVLDB 2015](https://www.vldb.org/pvldb/vol9/p204-leis.pdf)), on all platforms but `SQLServerFlat`.
JOB is a [dataset folder](#your-own-dataset), [`datasets/job/`](datasets/job/): its join graph and filters are derived
from the 113 JOB queries, and so is its input workload, [`input-workloads/job/`](input-workloads/job/), so generated jobs have 1 to about 16 joins, as in JOB. The data
(the 21 IMDB CSV files of the original dump) and the queries are not included. Its
[README](datasets/job/README.md) says where to get them and how to measure the statistics on your copy of the data.

### Your own dataset

Any dataset can be added as a folder `datasets/<name>/` with its `schema.sql` (`CREATE TABLE` statements), seed
queries (`queries/*.sql`, select-project-join queries with filters and aggregates) and, optionally, `dataset.json`
(file format and overrides). No code is needed:

```bash
python -m datafarm.datasets.add_dataset datasets/<name> --data /path/to/data
python RunGenerator.py --dataset <name> --platform Wayang
```

`add_dataset` derives the join graph from the queries' equi-joins and the foreign keys, the filter candidates from
the queries' predicates, and the group-by fields and statistics (row counts, selectivities, distinct values) from the
data. Unless another input workload is chosen, the seed queries are also what DataFarm learns the shape of the
jobs from. The jobs run
on all platforms but `SQLServerFlat` and compute the same result on each. [`datasets/README.md`](datasets/README.md)
describes the format, and [`datasets/example/`](datasets/example/) is a small example with data, which CI runs on
every platform.

- **Column types:** integers, decimals, dates, timestamps (with milliseconds) and text. Other types are read as text.
- **Input workload:** chosen separately with `--workload`. By default it is `input-workloads/<name>/` or the
  dataset's seed queries.
- **Limitations:** a job is a chain of joins in which each join uses a column of the table joined last (the generator keeps the right-hand row of each join), so star-shaped
  queries become chains.

### IMDB (Kaggle)

`--dataset IMDB`. The IMDb dump from Kaggle (`title.basics`, `title.ratings`, `name.basics`, ...), inherited
from the original DataFarm. Flink only, and not maintained or tested in DataFarm-X. For IMDB data, prefer the JOB
data manager.

## Labeling jobs

`RunLabelForecaster.py` labels the generated jobs with their run times. It runs an initial sample of jobs, trains a
quantile regression forest on their run times, and then repeatedly runs the jobs it is most uncertain about until
the model's uncertainty stops improving. The result is `final_dataset.csv` with measured or predicted run times for
every job.

Labeling is optional: the generated jobs and `generated_jobs_info.json` are usable on their own. It currently
labels **Flink jobs on TPC-H** only, and submits them through `datafarm/execution/flink/BuildAndSubmit.py` to a
running Flink 1.10 cluster. For Spark, Wayang and SQL (DuckDB, PostgreSQL, SQL Server),
`datafarm/execution/spark/run_spark_jobs.py`, `datafarm/execution/wayang/run_wayang_jobs.py` and
`datafarm/execution/sql/run_sql_jobs.py` run the jobs and report their run times.

```bash
pip install -r requirements-labeling.txt   # Python 3.6-3.8: the labeling code needs scikit-learn 0.22
python RunGenerator.py --platform Flink --dataset TPCH
python RunLabelForecaster.py               # --experiment <name> if you generated with --experiment
```

The results go to `training-data/Flink_TPCH/label_forecaster_<timestamp>/`. Settings in `CONFIG.py`:

- `FLINK_HOME`: the Flink installation (the folder containing `bin/flink`).
- `GENERATED_JOB_INPUT_DATA_PATH`: the folder with the TPC-H `.tbl` files the jobs read.
- `DATA_ID`: the TPC-H scale factor of that data, an entry of `datafarm/datasets_metadata/tpch/TableMetaData.py`
  (e.g. `"1GB"`); the label forecaster uses its table cardinalities as features.
- `LOCAL`, `LOCAL_HEAP`, `PARALLELISM`, `FLINK_TASK_MANAGER_URL`: how jobs are submitted and monitored.

- `INIT_JOBS`: number of jobs sampled and run before active learning starts.
- `MAX_ITER`: maximum number of active-learning iterations.
- `MAX_EARLY_STOP`: number of early-stop signals before the process stops.
- `EARLY_STOP_TH`: early-stop threshold, between 0 and 1.
- `RANDOM_INIT`: sample the initial jobs at random instead of by clustering.
- `RANDOM_SAMPLING`: pick the jobs to run by weighted random sampling based on uncertainty.
